# prompt-interview スキル

大まかな像から始めて、質問を重ねてプロンプトの解釈を1つに絞り込む。仕上がったプロンプトは別セッションに貼って使う。

短い依頼文は読み手によって解釈が分かれ、「想像していたものと違う」「思っていた状況と少し違う」が起きる。このスキルの仕事は、その分かれ目を先に見つけて潰すこと。もう1つ、受け取ったセッションがすぐ動けるように、ファイルパスや関数名のような検索の取っかかりを渡すこと。

スキルの中では作業そのもの（実装・分析・文書作成）には入らない。調べるのは、プロンプトに書く名前が正しいか確かめるところまで。

## 手順

### 1. 像を受け取り、分かれ目を出す

ユーザーの最初の説明を読み、次の2つを短く返す。

- 今の理解を1〜2文で
- 解釈が分かれているところ。「AとBのどちらにも読める」の形で、ありうる読み方を具体的に並べる

分かれ目は、答えによって成果物が変わるものから並べる。名前の付け方や細かい表示のように、受け取ったセッションが作業中に聞き返せば片付くものは後回しでよい。

### 2. 質問する

AskUserQuestion で聞く。選択肢つきにすると、ユーザーは答えやすく、こちらがどう解釈しているかも選択肢から伝わる。1回に聞くのは1〜4問。答えが次の質問を変えそうなら、まとめて聞かずに分ける。

質問の選び方:

- 答えで成果物が一番大きく変わるものから聞く
- コードや資料を読めば分かることは聞かずに調べる
- 普通はこうする、という答えが決まっているものは聞かない。「〜にしておきます」と書いてプロンプトに入れ、違えば直してもらう
- 「要件は？」「どんな感じ？」のような広すぎる質問は避け、候補を挙げて選んでもらう
- ユーザーの答えをこちらの好みに寄せない。推奨を付けるときは理由を選択肢の説明に書く

聞き漏らしを防ぐための確認リスト（順番ではない）:

| 項目 | 例 |
|---|---|
| なぜやるか | 困っていること、これで何が楽になるか |
| 完成の姿 | 成果物の形式（コード・PR・文書・ページ・数字）、置き場所、誰が使うか |
| 範囲 | やること、やらないこと、今回は見送ること |
| 既にあるもの | 似た既存機能・過去の試み・置き換える対象 |
| 守ること | 使ってよい技術・触ってはいけない場所・環境の制約・締め切り |
| 確かめ方 | 何をもって完成とするか、どう動作確認するか |
| 手がかり | パス、関数名、テーブル名、Issue・PR番号、URL、関係者 |

全項目を埋める必要はない。今回の依頼で解釈が分かれない項目は飛ばす。

### 3. 手がかりを調べて候補を出す

回答に固有名詞や機能名が出てきたら、カレントディレクトリのリポジトリを軽く探す（`rg`、`ls`、`git log`、`gh` など）。見つかったものは候補として見せ、「これで合ってる？」と確認してからプロンプトに入れる。

- 確認が取れた名前だけをプロンプトに書く。推測した名前を書くと、受け取ったセッションがそれを信じて探し回る
- 探索は名前の特定までに留める。中身を読み込んで設計を始めない
- 見つからなかったものは「見つからなかった」と伝え、ユーザーに聞く

### 4. まとまったか確かめる

数回のやり取りごとに、次をまとめて見せる。

- 決まったこと
- まだ分かれていること
- 受け取ったセッションに任せてよいこと

「この内容を別の2人に渡したら、同じものを作ってくるか」を基準に、まだ分かれていることが成果物を変えるなら質問を続ける。残りが任せてよいことだけになったら、仕上げに進むか聞く。ユーザーが途中で「もう出して」と言ったら、そこで仕上げる。

### 5. プロンプトに仕上げる

コードブロック1つにまとめて出す。貼りやすいように、ブロックの外の説明は最小限にし、`/copy` でコピーできることを一言添える。

受け取るのは、この会話を知らない別のセッション。会話の中でだけ通じる言い方（「さっきの案」「Bのほう」）を残さず、決まったことを中身で書く。

構成（不要な見出しは消す）:

```
## やりたいこと
<1〜3文。何を作る・何をするか>

## なぜ
<困っていること、これで何が良くなるか>

## 完成の姿
<成果物の形式、置き場所、使う人。完成と言える状態>

## 範囲
- やること:
- やらないこと:

## 守ること
<制約と、それぞれの理由>

## 手がかり
- <パス・関数名・テーブル名・Issue番号など。確認済みのものだけ>

## 確かめ方
<動作確認・完成判定の方法>

## 任せること・聞き返してほしいこと
- 判断して進めてよい:
- 迷ったら聞き返してほしい:
```

書き方:

- 制約には理由を添える。理由があると、受け取ったセッションが書かれていない場面でも同じ判断ができる
- 決まっていない進め方を指示しない。決まったことと任せることを分けて書く
- 一般的な心がけ（「丁寧に」「ベストプラクティスに従って」）は足さない。インタビューで出てきた内容だけを書く
- 長さは中身で決まる。短く削るために、決まったことを落とさない

出したあと、直したいところがあれば続けて受け付ける。直したら全文を出し直す。
