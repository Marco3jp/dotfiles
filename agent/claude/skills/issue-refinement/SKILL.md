# issue-refinement スキル

着手前のストーリーを読んで、次の2つを並べて出す。

- **進むなら**: このまま開発を進める場合に、先に決めないと手戻りが大きいこと
- **戻るなら**: 立ち返ってやりたいことを整理し直す場合に、問うべきこと

実装の細部（命名、表示の細かい仕様、APIの形など）は、実装中にエージェントが聞き返せば片付くので原則出さない。このスキルが見るのは、やりたいことの整理そのものに問題がないか、効果を確かめられるか、という実装より手前の部分。

スキルは答えを出さない。課題の定義し直しや解決策の提案はせず、「ここを詰めると選択が変わる」という問いとして出す。決めるのは担当者。ただし、このまま進めると作り直しになる見込みが高いなら「戻ったほうがいい」とはっきり書く。

## 環境ごとの補足

Issue の書かれ方、Issue の種類、コードの構成、使っているツールは環境によって大きく違う。どこを重く見るかはそれで決まるので、最初に補足を探して読む。

- 作業ディレクトリから上へ遡って `.claude/issue-refinement.md` を探す
- 見つかったら、そこに書かれた見方をこのスキルの手順より優先する

補足は次の見出しで書く。

1. **Issue の置き場と書かれ方**: リポジトリ、テンプレート、書き手の癖、親子や連番の付け方
2. **Issue の種類**: 種類ごとの見分け方、重く見るところ、「戻るなら」を出すかどうか
3. **コードの見方**: サービスの構成、レガシーな実装、インターフェース定義（proto / GraphQL / OpenAPI など）の場所、DB スキーマの場所、ログの探し方
4. **使っているツール**: 仕様やデザインが置かれる SaaS と、読めないときに誰に何を頼むか
5. **進むなら、で特に見ること**: その環境で手戻りになりやすいこと

補足が無ければ、Issue とリポジトリを見て 1〜5 を自分で組み立て、その見立てをレポートの冒頭に短く書く。見立てが外れていれば担当者が直せるようにするため。

## 手順

### 1. Issue を読む

Issue 本文・ラベル・担当者・コメントを読む。複数 Issue は並列に取る。親Issue・兄弟Issueが分かれば、それらも読む。

### 2. どう見るかを決める

補足（または自分で組み立てた見立て）に沿って Issue の種類を1つ決め、重く見るところを決める。テンプレートではなく中身で決める。どの種類にも当てはまらないなら、その旨を書いて問いを出す。

### 3. 調べる

問いの答えを左右する事実は、追える限り追う。問いに関係しない調査はしない。

- 既存の実装・似た機能・既存のログがあるかをコードで確かめる
- データの取り方が問いになるなら、そのデータを書き込んでいるコード・バッチ・外部連携まで遡り、どこから入ってくるのかを確かめる
- 範囲が問いになるなら、候補をコードから洗い出して一覧にする。人が線を引くのに要る性質も添える（API なら出口ごとの認証方式、DB を読むか、など）
- 対象が手元に無いリポジトリにあるなら、`gh repo clone` で scratchpad に取ってきて読む

背景の数字を出す分析まではしない。「この数字を見れば背景を確かめられる」と書くところで止める。

#### 読めなかった資料

画像・ドキュメント・チャットのスレッド・クラウドのリソースなどが読めなかったら、問いに効く情報が載っていそうかを見積もる。重要そう、または重要か判断がつかないなら、レポートを書く前に人間へ「何を読めるようにしてほしいか」（貼ってほしい画像、付与してほしい権限、ログインしてほしいサービスなど）を伝え、読めるようになってから続ける。

人間に聞けない状況（サブエージェントとして動いているなど）なら、レポートの冒頭に、読めなかった資料と読めるようにするために必要なことを書く。

### 4. 問いを出す

#### 戻るなら（やりたいことの整理）

- **背景が具体的か**: 困りごとが実際の事象・問い合わせ・数字で書かれているか。「〜したい」「〜が課題」だけで、誰がどれくらい困っているかが無いなら、それを問う
- **課題を詰め込んでいないか**: 1つの機能に別々の課題がいくつも乗っていないか。課題ごとに分けると別の解決策になる、あるいは一部だけで足りるなら、分けて考える余地を出す
- **Why と How が噛み合っているか**: タイトルや本文の解決策（How）は誰かの一案であって確定要件ではない。困りごとの記述やコメントの動機から本当に解決したいこと（Why）を取り出し、How でそれが片付くかを見る。コメントの一文に本当の動機が潜み、タイトルと食い違うことが多い
- **真因が分かっているか**: 「遅い」「失敗する」「使われない」系で、原因を切り分ける前に対策が決まっていないか
- **効果をどう確かめるか**: アウトカムの指標があるか。その指標を今のログ・データで出せるか（既存ログの有無はコードで確かめる）。仮説が外れたときにどうするかが書かれているか
- **軽い代替案で足りないか**: 却下された案が本当の課題には十分なのに、別の理由で却下されていないか。却下理由を言葉にしておかないと実装者が止まる

#### 進むなら（先に決めないと手戻りが大きいこと）

どの種類でも出す。実装中に聞き返しても間に合わないものだけ。

- 外部の会社・他チーム・別アプリのリリースに依存していて、その仕様や時期が決まっていない
- 複数のリポジトリやシステムにまたがり、リリース順序が決まっていない
- 影響する人への連絡やヘルプの更新が要るのに決まっていない
- 本番でしか確かめられない部分があり、その確かめ方が決まっていない
- デザインが無い、または仕様で触れている要素がデザインに無い
- 最小スコープと将来の拡張の線引きが無く、着手後に仕様が膨らみそう
- Issue を書いた後に、Issue が当てにしている仕組みが変わっている
- 移行なら: 順序、旧データの扱い、ロールバック、呼び出し元の漏れ
- データ作業なら: 抽出条件の曖昧さ、件数の見込み、再実行時の挙動、実行後の確認方法

命名、細かい表示仕様、バリデーション、APIの形のように実装中に決めて差し支えないものは出さない。

### 5. 所見を決める

レポートの冒頭に、次のどれかを1つ書く。

- **進んでよい**: 戻るなら、の問いが無いか軽い。進むなら、の問いを片付ければ着手できる
- **進みながら確かめる**: 戻るなら、の問いはあるが、着手と並行して担当者に確かめれば済む
- **戻ったほうがいい**: 背景が無い、課題が詰め込まれている、効果を確かめる手段が無い、真因が分からないまま対策が決まっている、などで、このまま作ると作り直しになる見込みが高い

## レポートの形

Issue ごとに1つ。

```markdown
# #<番号> <タイトル>

種類: <種類> / 担当: @<担当者。いなければ「未設定」>

**<所見>**: <1〜2文。なぜその所見かを、下の問いのどれに拠るかで書く>

## 戻るなら

1. **<問い>**
   <Issueから読み取れたこと、調べて分かったこと>
   <この問いへの答えで何が変わるか>

## 進むなら

1. **<決めること>**
   <Issueから読み取れたこと、調べて分かったこと>
   <決まらないと何が手戻りになるか>

## 調べて分かったこと

- <既存実装の場所、データの入ってくる元、候補の一覧、関連Issue。問いに使ったものだけ>
```

- 補足が無く見立てを自分で組み立てたときは、所見の前に見立てを2〜3行で書く
- 戻るなら、を出さない種類、または問いが無いときは、その見出しごと消す
- 進むなら、の問いが無ければ「先に決めることはない」と1行書く。何も書かないと未確認と区別できない
- 事実と推測は混ぜない。コードやIssueで確かめたことはそのまま書き、確かめていないことには「（推測）」を付ける
- 調べたことは、どこまで追えたかが分かるように書く（「`<テーブル>` は `<バッチ>` が `<外部サービス>` から書き込んでいる」「書き込み元はこのリポジトリに無く、ここで止まった」）。追えなかった先を推測で埋めず、確かめる手段を書く
- 問いは多くても各5件まで。重いものから並べる。議論済みと読み取れるもの、答えで作るものが変わらないものは出さない

## やらないこと

- Issue 本文の書き換え
- 課題を定義し直した案や、代わりの解決策の提示
- ストーリーの是非・優先度の判断
- レビュー段階の PR の確認
