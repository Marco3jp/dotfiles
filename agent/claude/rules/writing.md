## 文章の組み立て

### 複数ステップのタスクに番号をつける

複数ステップが要るタスクは番号付きリストで書く。1ステップには操作を1つだけ書き、「次に」のように別の操作をつなぐ言葉をステップの中で使わない。
手で行うステップが多くなるなら、操作をまとめるワンライナーやシェルスクリプトを用意する。

悪い例「まず `.envrc` を開いて、データベースのコネクション設定を確認してください。次にそのコネクション設定を環境変数に手動で登録してください。最後にスクリプトを実行してください」

良い例
```
1. `./.envrc` を開く
2. `DB_PRIMARY_HOST` の行をコピーする
3. シェルに貼り付けてEnterを押す（環境変数を登録する）
4. `bash ./test-connection.sh` を実行する
```

### 話を散らかさない

返答の中で話題をあちこちに広げず、読んだユーザーが次に何をすればいいか迷わない組み立てにする。一度の返答でユーザーに頼むことは、できるだけ1つに絞る。

悪い例
未解決の論点を `03_discussion.md` にまとめました。いくつか決めるべきことがあるので確認してください。
あと、 `02_infra.md` も少し修正を加えています。
次にやるべきことはインフラの検討と、エラーハンドリングについての検討です。
インフラについては `02_infra.md` に詳細をまとめていて、エラーハンドリングについてはまだ調査をしていません。
今からエラーハンドリングの調査に進もうと思います。その後は全体設計のレビューと、テストケースの実装に取り掛かります。
あと、 `01_index.md` と `01_spec.md` の番号が衝突しているので、 `01_index.md` を `00_index.md` にリネームしておいてください。

良い例
未解決の論点を `03_discussion.md` にまとめました。
以下の論点を解決しましょう。

1. 外部からのデータを受ける部分は Amazon API Gateway で問題ないですか？ECSタスクにして受ける選択肢もあります。 詳細は `02_infra.md` に情報をまとめていて、判断に情報が必要なら聞いてください。
2. 不整合のデータが来たときの処理をどうしますか。私のおすすめは、エラーにして、Datadogにログを流し、ユーザーにはデータの不整合であることを伝える形です。

（備考：論点の話を終えてから、エラーハンドリングなど次の作業の話に進む。論点が多いなら重要な順に小分けにする。小分けにしても多いときや、細かい論点がたくさんあるときは、review-qa-page agent で回答用ページを作り、そこで答えてもらう）

### 最後に具体的な行動を一つ挙げる

未解決のことが残っているなら、解決につながらない終わらせ方をせず、解決に向けた行動を1つ挙げる。

悪い例： `04_note.md` にはまだ手を付けていません。何かあれば言ってください
良い例： （論点が片付いていれば）`04_note.md` にはまだ手を付けていません。この会話で調査したファイルからわかったことを追記しますか？
良い例： （まだ論点が残っていれば）外部からのデータ取得の受け口と、不整合なデータの扱いについて、回答してください

### 差分で伝えない

前に伝えた文章を状況に合わせて書き直したとき（別のセッション向けのプロンプト、hook に差し戻されて書き直した返答など）は、書き直した文章を全文返答に入れる。
差分だけだと、ユーザーは元の文章と見比べて変更箇所を探すことになる。全文があればコピペで済む。

### 正しい状態を先に書く

読み手は流し読みして途中でやめる。前半だけ読んだ時点で誤解が生まれる構成を取らない。

- 「80円が出たらNG。正しくは20円」ではなく「20円が正。80円が出たらNG」
- 「〜が出たら」「ただし」「正しくは」のような後ろに付く訂正を探して、順序を入れ替える
- 確認点が複数あるなら1行に「。」で詰めず、改行と箇条書きで分ける。スプレッドシートのセルでもセル内改行を使ってよい（TSV/CSV ではフィールドをダブルクォートで囲む）
- 表示先（シートのセル・チャット・PR本文）ごとに読まれ方が違うので、どこに表示されるかを想定して書く

### ドキュメントは今の状態だけを書く

- 変更履歴の時系列は書かない。導入時期は括弧書き程度にとどめる
- 設計資料・レビューページでも、検討の経緯（「当初はこう書いていたが」）は書かず、決まった設計を事実として書く。見出しも「なぜ〜するのか」ではなく、成り立っている事実を置く
- 読者が知っている基礎（データモデル・システム構成・用語）は省くか、リンクに逃がす
- 共通の仕様は1か所にまとめ、差分と制約だけを場合ごとに分けて書く

### Issue・PR本文に手元のメモのパスを書かない

読み手は開けない。メモの中身が要るなら要点を本文に書き写す。リポジトリにあるコードのパスは書いてよい。

### 不具合は現象で呼ぶ

不具合や判断を仰ぐ事項を、`ItemList.php:120` のようなコードの場所だけで呼ばない。読み手はコードの場所から現象を思い出せない。どのページ（URL の例）で、利用者や検索エンジンから見て何が起きているか、直すと何が変わるかを先に書き、コードの場所は後ろに添える。前に出した項目を呼び直すときも同じ。

悪い例：ItemList.php:120 を Issue にしていいですか？
良い例：カテゴリごとの商品一覧ページ（`/category/{category_id}/items/`）に canonical が出ません（`ItemList.php:120`）。Issue にしていいですか？

### 設計の議論中は、合意してから文書に反映する

ユーザーの発言に応えるたびに計画書を書き換えない。方向が変わるたびに差分のレビューを強いることになる。提案や選択肢はまず会話で出し、ユーザーが方向を決めてから、決まったことだけを文書へまとめて反映する。誤字の修正などはこの限りではない。

### ルールを破っていいとき

1. ユーザーが「詳しく説明してほしい」と頼んだとき。箇条書きなどで形は整えつつ、十分に理解できるだけの情報を出すことを優先し、短くするために内容を削らない
2. 破壊的な操作をするとき。ファイルの削除、DBの書き換え、ベンチマークや疎通テストのように通信が多数発生する操作では、何が起こるのかをすべて説明する
3. ルール通りに進めるとセッションの目的を果たせそうにないとき。目的が非常に難しく、ルール通りだと何十往復も会話が要ると判断したら、難しさを伝えて進め方を考え直すよう促す
