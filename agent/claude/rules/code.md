## コード

### コメント

- 基本はコメントを書かない。既存のコメントは、変更で嘘にならないなら触らない。嘘になるなら直す
- 読んだ人が「なぜこうなっている？」と引っかかる箇所にだけ理由を書く。理由は因果の根元で書く（「使う処理が無いから」「呼び出し元が社内だけだから」）。設定・型・構成が無いことは結果なので、理由にしない
- 既にある構造に仕方なく合わせているなら、その構造を理由に書いてよい。外せる条件が分かるなら1行添える
- 作りたい形が先にあって構成がそれに従っているなら、構成の話はコメントに書かない
- 別リポジトリの内部事情は書かない。そちらが変わった瞬間に嘘になる
- interface 定義（proto / OpenAPI など）には受け付ける値の範囲を書く。今の呼び出し元の事情は書かない。呼び出し元が増えたら嘘になるうえ、サーバが実際に受け付ける範囲と食い違うことがある
- 例を見せたほうが早いときは、例を書いてよい

```
✗ // primary への接続設定をまだ用意していないので replica だけにする
○ // primary を使う処理が無いので replica だけに接続する。書き込みが要るようになったら NewConnManager に替える

✗ // limit: 1〜50。一覧画面が 50 件ずつしか取らないため 50 を超えることはない
○ // limit: 1〜100。省略時は 20
```

### 副作用のあるスクリプトは実行モードを明示フラグにする

課金や副作用を伴うスクリプトで、位置引数の有無や暗黙のデフォルトで dry-run と本実行を切り替えない。`--dry-run` / `--run` を必須にし、無指定は usage を出して exit 2 にする。コマンド行を見ただけでどちらを実行したか分かるようにするため。課金のあるクエリなら、`--run` のときも先に dry-run でスキャン量を出してから本実行する。

### データを書き換えるSQLは、各クエリの直前に読むべきことを書く

DELETE / UPDATE を含むSQLを人に実行してもらうときは、各クエリの直前に次の3点をコメントで書く。後ろや行末に書くと、結果を見た後に読まれて見落とされる。

1. 何を実行・確認するクエリか
2. 期待される結果（行数・Affected rows などの具体値）
3. どんな結果なら異常か、そのときどうするか（ROLLBACK して連絡、など）

`BEGIN;` / `COMMIT;` も独立した手順として区切る。
