## 作業の進め方

### ツールがタイムアウトしたら止まって声をかける

承認ダイアログが出るツールは、承認が間に合わないだけでタイムアウトすることが多い。タイムアウトを見たら、リトライも別の経路探しもせず「承認が間に合わなかったかもしれないので、再開していいか」と聞いて待つ。クエリを軽く書き直したり、認証情報や別のデータソースを探しに行ったりしない。接続そのものを疑うのは、ユーザーが接続断だと言ったときだけ。

### 決まった方針に当てはまる件は聞かずに当てはめる

ユーザーが一度決めた振り分けの方針（例: 「旧バージョンでも動く修正は、互換対応のブランチの PR に入れる」）に当てはまる新しい件は、確認を取らずに方針どおりに置き、「方針どおりこう置いた」と報告する。報告の前に、計画書の「ユーザーが決めたこと」などを見て当てはまるか確かめる。

当てはまらず聞くときは、push・PR や Issue の本文の更新など外に出す操作を止めてから聞く。push してから「移す？」と聞くと、やり直しの手間をユーザーに押し付けることになる。

### コミットはトピックごとに分ける

「設定値の渡し方を変える」「エラーハンドリングと再送」のように、同じ話題の変更を1コミットにまとめる。大きな話題が2つ以上混ざっていれば `git add -p` などで分ける。レビュー指摘1件ごとの細切れにはしない。小さな変更がいくつかあるだけなら1コミットでよい。push 済みのものは force push してまで分け直さない。

### メモリのインデックスは短く保つ

MEMORY.md は毎セッション読み込まれるので、1行は「タイトル＋読みに行くか決められる短いフック」だけにする（目安80〜120バイト）。実値・パス・手順は個別ファイルに書く。

月1回くらいで見直す。

1. インデックスと実ファイルを突き合わせる。行が無いメモリは思い出されない
2. project タイプで案件が終わったものは消すか、要点だけ reference に縮める
3. 90日更新されていないファイルは、中身が今も正しいか見る
